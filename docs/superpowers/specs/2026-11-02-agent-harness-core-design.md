## Problem Statement

TinyIoTHub 的 Harness 层不是一个统一运行时，而是一组散点能力：Chat 与 Task 两套事实、`TurnEvent` 只进内存 trace、工具清单硬编码、审批分为 Task 与 heartbeat 两套、没有回放/分叉、没有 Harness 级扩展模型。IoT 设备层（声明、Hub、Job/Watch、证据链）已基本完整，缺口在 Harness。

判断标准不是"有没有某个功能"，而是这些能力是否长在同一套**会话事件 → 状态机 → 控制 → 投影**契约上。按 AGH 公开的 as-built 报告与 OpenHands/Claude/OpenAI/LangGraph 的公开设计对照，本仓在事实主干、恢复语义、工具运行时、上下文管线、扩展模型与 Trace 上都不成立。

## Demand Evidence

内部平台诉求，不是外部客户需求。用户原话：

- "我不需要修修补补的解决方案，我需要完整的解决问题。"
- "现在我觉得我们当前的设计很乱，感觉什么都有了，又完全没有达到我的预期。"
- "抛开物联网本身的能力，因为这部分我感觉是完整的，或者后续可以补充。现在 harness 的能力达不到我的预期。"
- "因为我们的项目当前还没有实际使用，所以不需要考虑迁移版本。"

没有外部付费客户、没有使用统计。本设计把自己当作内部平台的第一个用户，用可运行的垂直切片验证，而不是用市场数据证明。

## Status Quo

- 没有主 Agent 的长期 Supervisor 与统一 `WorkflowDefinition`，巡检、视频、协同和节能无法仅靠配置持续运行；现有触发器与一次性 Task 不等于 24x7 工作系统。
- 新增一种设备能力通常要改工具清单（`autonomous_factory.rs`）、宪法提示词、前端事件名单，再重启；不是配置驱动。
- Chat 事实在 `chat_sessions/chat_messages`，Task 当前状态在 `agent_runs`（已有 `running/interrupted`）；但模型思考、文本、工具调用等 Step 过程未完整进入持久事件流，不能完整回放。
- `hub_ledger` 是设备遥测账本（2026-11-02 本地库实测：`state_change` 3,142,915 行；按日统计 2026-10-31 与 11-01 各约 100 万行；库文件 1.1GB。查询：`sqlite3 data/tinyiothub.db "select kind,count(*) from hub_ledger group by kind"` 与按 `substr(ts,1,10)` 分组），不是 Harness 事实主干；两者混用会让写入、索引与回放互相污染。目前 `runtime.v1` 的 Task/Job/审批事件也写在这里（`crates/db/src/runtime_event.rs`），第一版全部迁到 `session_events`。
- 审批与决策分成 `task_approvals` 与 heartbeat approvals；没有统一的 decision register，也没有"未知效果人工对账"。
- 所有 Harness 表在不同 workspace 间共享一个 SQLite 文件，靠 `workspace_id` 过滤；备份、保留、故障与写入不能按工作区独立。
- 没有分叉/回退、没有会话搜索、没有 Harness 级插件清单与版本固定。

## Target User & Narrowest Wedge

**目标用户**：维护 TinyIoTHub 平台的内部工程师与运营者。不是外部客户角色，没有名字、没有付费证据。

**最小楔子**：用**一个持续巡检 Workflow + 一个多设备受控动作 + 一次进程重启**证明 Harness Core 的五件事同时成立：

1. 系统启动即加载 enabled workflows，主 Agent 长期 loop；每个具体任务由全新上下文的 Subagent 执行，不需要人工发起第一次 Run。
2. 每个 Run 的全部执行事实（思考、文本、工具调用、结果、设备动作、审批、效果）进入该 workspace 的事件账本，主 Agent 只保留可压缩/清理的投影。
3. 前端按事件流实时投影出完整过程，刷新/重连后能续上，历史可回放。
4. 进程在设备动作中途崩溃后，重启能恢复 workflow 调度与当前 Run；未知结果先对账，不重复执行。
5. 该 workspace 的工作流、事件、效果、决策、任务、Job 全部落在自己的存储里，可以独立备份与恢复；新增一个视频或节能工作流只改配置，不改 Rust/Core 或前端事件名单。

## Constraints

- Rust 2024 workspace；SQLite（WAL）；单实例进程锁；无外部消息队列。
- 项目尚未实际投入使用：**不做历史数据迁移与向后兼容**，可以直接重设 schema 与模块边界。
- 继承 IoT 设备层：设备声明、Hub、Job/Watch、证据链、驱动 manifest 保留；Harness 不反向依赖设备实现。
- 不新增固定 Task/媒体/事件配额；容量用背压、指标与告警表达。
- 用户可见文案中文；错误必须可解释，不允许静默失败。
- 前端 Lit 3 + Vite；构建需 Node 24。

## Premises

1. **产品缺口在 Harness 层，不在 IoT 能力层。** 传感器/视频/模板/驱动可以后补，不作为本轮设计中心。
2. **目标是 AGH 级 Harness 行为**：持久会话账本、可插拔 Loop、工具/扩展运行时、统一审批/沙箱、Trace/回放/steering。
3. **现有 `crates/agent` 不能靠补丁变成 Harness。** 需要先定义 Harness Core 边界，把现有 thing-agent 作为第一个应用接入；设备声明与 Hub 语义继承。
4. **"配置大于约定"落在 Harness 扩展面**：工具、Loop、流程、上下文段、面板都由声明/端口生成，Core 不写死设备或场景。

用户已确认以上四条成立。

## Approaches Considered

### 事实主干

- **纯事件溯源**：一切从事件重放。透明度最高，但事件量、schema 演进与启动重放成本最高；对 100 万行/天的平台偏重。**被否决为第一版**。
- **Checkpoint 为主**：每步快照恢复，事件仅作投影。实现最轻，但过程叙述不完整，回放/审计要另建事件。**被否决**。
- **混合主干（选定）**：`session_events` 为唯一事实，`projection_snapshots` 只加速启动，`effect_intents` 管副作用。

### 存储隔离

- **单库 + workspace_id 逻辑隔离**：简单，但备份/保留/故障不能按工作区独立。**被否决**。
- **每 workspace 一个 Harness 完整库（选定）**：任务、outbox、run、审批、决策、效果、事件、Job、媒体元数据同库；全局库只留租户、用户、设备目录、驱动、声明、模板。

### 变更策略

项目未投入使用，**不做迁移与版本兼容**；直接按目标 schema 实现。

### 持续工作形态（D8）

- **单个无限 LLM 会话**：所有任务共享主上下文，成本、错误与历史持续累积，恢复困难。**被否决**。
- **纯代码 Scheduler**：能持续调度，但缺少主 Agent 汇总结果、跨任务推理和协调的位置。**不作为完整目标**。
- **主 Agent + 独立 Subagent（选定）**：主 Agent 长期 loop、每轮有限调用；每个任务由全新上下文的 Subagent 执行。主上下文是可重建投影，持久 workflow/task/events 才是事实。v1 只许两层，不递归 Subagent。

## Recommended Approach

**两层持续 Agent + 声明式 Workflow + 混合事件主干 + 每 workspace 完整 Harness 库 + 清晰的 Core/应用边界。**

### 持续 Agent 与声明式 Workflow

```text
WorkflowDefinition（workspace DB，enabled/version 固定）
          ↓ 系统启动加载
Host Supervisor（精确 cron/watch/event 调度，空闲时不调用 LLM）
          ↓ 持久 wake + workflow/slot/event 幂等键
Main Agent（长期 loop，每轮有限调用；只看可重建投影）
          ↓ parent_task/parent_run + 明确输入，不共享对话上下文
Subagent（每次全新上下文，执行有限 Task Run）
          ↓ reason → act → tool → result → continue（直到本子任务完成）
结构化 TaskOutcome + evidence refs + 新事件
          ↓
Main Agent 汇总并协调后续 Workflow；压缩/清理自己的上下文
```

- `agent_workflows(workflow_id PRIMARY KEY, enabled, current_version, updated_at)` 只是 workspace DB 中的 current/enabled 指针；不可变 `workflow_revisions(workflow_id, version, definition_json, created_at, PRIMARY KEY(workflow_id, version))` 保存每次定义。`agent_tasks` 增加 `workflow_id/workflow_version/parent_task_id`，`agent_runs` 增加 `parent_run_id`，事件用 `cause_id` 串起主/子因果。编辑追加 revision 并移动 current 指针，不覆盖旧定义；被任何 Task/Run 引用的 revision 不得删除。
- 定义只包含声明数据：`objective`、`trigger(cron|watch|event)`、`device_selector`、`source_selector`、`tool_ids`、带版本的 `skill_refs`、`required_capabilities`、`approval_policy`、`evidence_policy`。巡检、视频问题发现、多设备协同和节能优化都是同一 schema 的配置实例，不分别创建 Rust loop 或场景专用表。
- **内置模板（X1，XD2 已批准）**：提供巡检、视频、节能三份版本化配置模板，运维复制后修改设备、数据源和策略即可运行。模板复用统一 schema/引用校验并有实例化与版本测试，不新增执行引擎或默认放开额外 Effect 权限。通用定义文件导入仍属 deferred X5，本期不实现。
- 代码负责精确的 cron/watch/event 下一次唤醒与 `workflow_id + trigger_id + slot/event_id` 来源幂等键，**版本号不进入来源身份**；首次持久 wake 时固定 revision，同一 slot/event 在编辑、回退或重启后仍返回原 Task，不重复物理动作。主 Agent 负责跨任务协调，不让 LLM 猜测时间或充当持久调度器。配置写入时校验引用的工具、Skills、设备/数据源选择器与策略，错误在保存时可见。
- Subagent 只接收本次 workflow 版本、设备/证据快照和必要上下文，返回 `{status, summary, observations, evidence_refs, recommended_actions}`。主 Agent 可以协调多设备后续任务；Subagent 也可以在一个 Run 内直接操作多台设备，不需要第三层 Agent。`recommended_actions` 不是执行许可，后续动作必须重新走工具策略、审批和 Effect 边界。
- **版本与启停**：Task/Run 创建时固定 workflow 版本，编辑版本只影响后续调度；禁用 workflow 只停止未来 wake，不隐式取消在途 Task/effect，显式取消仍走统一控制契约。调度 slot 使用 UTC 与确定时区配置，重复 slot/event 由唯一幂等键去重。
- **Misfire（XD8=B）**：停机、禁用或时钟前跳期间过期的 cron slot 全部跳过并写 `trigger.missed`，不补最新、不补齐历史；回拨不得重发已持久 slot。持久 watch/event 只按原 source seq/id 重放并去重，缺口或不可读时告警并标记 `trigger.unavailable`，不合成 Task/Effect。多 slot、禁用、编辑、回拨和事件缺口均有重启 E2E。
- **父子生命周期**：Subagent 的 TaskOutcome、结果事件与 parent wake 同事务提交；主任务取消在同一 workspace DB 内级联子任务 `cancelling`，只有全部子任务及其 owned effects 明确终态后父任务才可结束。v1 禁止子任务再创建子任务。
- **调度背压**：主 Agent 只在配置/事件/子任务结果到来时做有限推理，空闲不调用 LLM；Subagent 启动沿用现有 scheduler/active-run 限制与持久 outbox 背压，不新增固定 Task 配额，并记录 pending/oldest wake、调度延迟和失败原因。
- **Harness session 身份**：每 workspace 一个持久 Supervisor/Main session，ID 为 `supervisor:<workspace_id>`；每个 Subagent Task/Run 使用新的 `task:<task_id>/run:<run_id>` session。workspace 级 `supervisor.tick_*`、`trigger.missed/unavailable` 使用 Supervisor session；Subagent 之间不共享 session 或对话历史，Chat session 不作为 Core 依赖。
- 主 Agent 上下文是 `projection_snapshots` 中的 Supervisor 投影，包含 workflow 版本、活动任务和最近结果引用。压缩/清理产生 `context.compacted` 事件，记录输入 seq 范围与快照引用；删除的是模型对话副本，不是事件、任务结果或工作流事实。重启后从持久数据重建。
- v1 不做通用动态插件包 DAG、递归 Subagent 或 UI 面板插件系统。`ToolDescriptor + WorkflowDefinition + skill_refs` 已覆盖配置扩展；设备安全联锁、资源仲裁与 e-stop 始终留在设备/驱动侧，Agent 不得绕过。

### Workflow dry-run（X2，XD3 已批准）

- dry-run 固定 workflow revision 和调用方明确选择的 `snapshot_seq`，复用生产 reducer、ToolDescriptor 和通用投影；snapshot 不存在或不可读时响亮失败。`execution_mode=simulation` 是 agent_tasks/agent_runs/session_events 的显式字段，事件包含输入 snapshot ID，不能与真实 Run 混淆。
- simulation 组合根不注册任何设备 worker/driver dispatcher，并在创建 prepared Effect 之前即拒绝真实 Effect/Decision 写入。simulation 不产生生产 wake/outbox、parent 协调动作或真实恢复任务；真实列表、恢复扫描和 Main Agent 投影默认只读 `execution_mode=production`，模拟 TaskOutcome 绝不能触发真实后续 Task/Effect。
- dry-run 用于配置、提示词、输出和投影验证，不证明真实模型、设备驱动或物理结果；UI 必须持续标注 simulation，不提供“批准真实执行”的捷径。模拟历史在事件库中不可变保留并默认隔离展示，不在 v1 删除或混入生产统计。

### 模型与视频能力

- ToolDescriptor 与 WorkflowDefinition 都可声明 `required_capabilities`；组合根从现有 provider/model 配置与 `supports_vision` 等能力端口解析实际能力，不在提示词中猜测。
- 保存时报告当前缺失能力；每次 Run 的 composition 再检查一次。缺失时在模型调用前写 `capability.unavailable`，Run 以 `failed(capability_unavailable)` 结束，不创建 Effect；Subagent/TaskOutcome 保留缺失能力名称与恢复建议。
- simulation 与 production 使用相同 capability 检查、错误事件和 UI 文案。视频模板必须声明视觉能力，非视觉 provider 不得编造观察结果；更换具备能力的 provider 后创建新 Run，不改写失败历史。

### Supervisor 健康面板（X3，XD4 已批准）

- 在现有 Runtime UI 显示下一次 scheduled wake、oldest pending wake、调度延迟、活动 Main/Subagent 与 parent/cause、最近错误和恢复入口。scheduled 只表示计划时间，不承诺准点执行。
- Host/Scheduler 健康来自进程健康与单条可变的 `supervisor_state` 当前状态行（tick_seq、last_started_at、last_completed_at、last_error），而不是 AI heartbeat；不要把每次 tick 追加进永久事件库。只有 `supervisor.stalled/recovered` 等状态变化写 session_events。进程内同时使用 monotonic clock 防瞬时回拨，持久 UTC 用于重启后判定；即使没有 enabled workflow 也执行轻量调度 tick，正常“下一 wake 很远”不判停滞。超过配置的 scheduler tick deadline 未完成、到期未开始，或持久时间回拨才显示 stalled/degraded；下一次成功 tick 清除恢复中状态。面板必须能区分“没有新 Run”与“调度器停滞”。
- dead wake 恢复沿用 Agent 管理权限和原 event_id 幂等 retry；空态、延迟、权限与恢复都有测试，不新增 UI 面板插件框架。

### 存储布局

```text
data/agents/<workspace_id>/
  harness/
    harness.db          # workspace 级唯一事实主干 + 状态机 + 效果 + 决策 + 投影快照
    harness.db-wal
    backups/            # 迁移前与按需 VACUUM INTO 快照
  memory/               # 既有 brain.db、response_cache.db、记忆文件
  uploads/  skills/  AGENTS.md  TOOLS.md  HEARTBEAT.md  USER.md

data/tinyiothub.db      # 平台库：tenants/users/workspaces 注册表/设备目录/驱动/声明/模板
data/tinyiothub.db.lock # 现有全局单实例锁，覆盖全部 workspace 库
```

工作区库中的表（第一版）：

```text
session_events        -- append-only 执行事实（替代 hub_ledger 中的 runtime.v1）
agent_workflows       -- current/enabled 指针
workflow_revisions    -- 不可变版本定义，供在途恢复与审计
effect_intents        -- 外部副作用状态机（dispatch 许可真源）
decisions             -- 唯一审批/决策真源（含 effect reconciliation）
commands              -- steer/interrupt/pause/cancel/queue 的持久命令与消费状态
supervisor_state      -- 单条调度健康当前状态；不逐 tick 追加永久事件
agent_tasks           -- Task 状态
task_wake_outbox      -- 持久唤醒
agent_runs            -- Run 当前状态（由事件折叠）
device_jobs           -- 设备动作事实
media_evidence        -- 证据元数据
projection_snapshots  -- 投影缓存，可丢弃重建
```

**Workspace DB 生命周期**：`Db` 仍是 AppState 唯一存储门面，内部持有平台 pool 与按 workspace 缓存的 pools，不新增第二套 Repository。workspace 创建时由 Db 创建 `harness/` 目录、建库并执行独立 Harness migrations；路径只能由注册表 workspace_id 派生。启动时枚举注册表，逐个打开、备份/迁移并恢复非终态 Run/effect；单个 workspace 失败只把该 workspace 标为 unavailable 并告警，其他 workspace 继续。pool 对象可缓存到进程结束，`min_connections=0` 与既有 idle timeout 释放物理连接；关闭进程时关闭全部 pools。删除 workspace 前先停止接入与运行时、关闭 pool、完成备份，再删除文件；不得删除后仍被请求重开。迁移使用现有 `VACUUM INTO` 机制，备份/恢复与跨 workspace 路由、故障隔离必须有真实 SQLite 测试。启动扫描的 workspace 数、迁移耗时与 pool/连接数进入指标；不新增固定 workspace 配额。

**独立恢复（restore）**：Db 先把该 workspace 标为 restoring，拒绝新请求/调度并防止 pool 重开；停止 Main/Subagent 和 worker 接入，对在途 Effect 按现有规则完成或对账为 unknown。随后关闭并 evict pool，保留当前 DB 为 rollback 文件；只有连接关闭后才处理旧 WAL/SHM，将 VACUUM INTO 生成的自包含备份原子替换为 harness.db，不从备份复制旧 WAL。重新打开并迁移、校验完整性、运行非终态 Run/Effect/Command 恢复，成功后才重新启用。任一步骤失败则回滚到保留的 DB 并重新打开，workspace 保持 unavailable 且告警；其他 workspace 全程可用。真实 SQLite 测试必须覆盖 active Run 的 restore、失败回滚与其他 workspace 隔离。

**Restore fencing**：备份之后的外部世界可能已经继续执行，恢复文件里的 `prepared/approved/requested` 不得直接获得 dispatch/consume 许可。恢复后所有非终态 Effect（包括 prepared）先置 `unknown/recovery_required`，Run 暂停、wake 保持、Command 不自动消费；按 effect_id/idempotency key/external_ref 对账后，才可形成明确终态或由人工决定后续。已终态记录不重复执行；调度游标从恢复时刻按 XD8=B 重新建立，旧 slot 不补跑。任何无法对账的恢复都保持 blocked 并告警，不能为了“继续进度”而自动派发。测试包含“备份后实际动作完成、再恢复旧文件”的场景，证明不会重复设备动作。

**换库崩溃恢复**：恢复前在平台注册表持久化 `restore_journal(workspace_id, epoch, phase, backup_path, rollback_path, updated_at)` 并同步目录。新备份先放入不含 WAL 的 `harness.restore/` 并校验；关闭 pool 后，将完整 live `harness/` 原子改名为 `harness.rollback/`，再将 `harness.restore/` 改名为 `harness/`，不得把单个 DB 与另一代 WAL/SHM 混用。每次 phase 变化同步更新 journal。若换库中崩溃，启动从 journal 判断 live/rollback/restore 目录及完整性，只选择一个完整目录继续；缺失或损坏时回滚到保留目录。workspace 在恢复完成前始终 unavailable，其他 workspace 不受影响。测试覆盖 rename 前、两次 rename 之间、改名后、journal 损坏与文件缺失；外部 Effect 仍受 Restore fencing 约束。

`task_approvals` 与 heartbeat approvals 在 v1 统一为 `decisions`，不保留第二套审批表。全局库不再保存 Harness 表；`hub_ledger` 继续只存设备遥测（是否也按 workspace 拆分留待后续，不在第一版）。`runtime.v1` 的 Task/Job/审批事件改由 `session_events` 承载，旧的 runtime_event cursor/投影读路径改为读 workspace 库。

**第一版 Chat 边界**：Chat 历史仍由应用的 `chat_sessions/chat_messages` 持有，不属于 Harness Core v1 的事实主干；本设计的"唯一事实"仅指 Harness Run（Task/Job/Effect/Decision/Step）。Chat 迁入事件模型作为后续轴，不在本设计里冒充已完成。

### 事件信封

```text
session_events(
  seq            INTEGER PRIMARY KEY AUTOINCREMENT,  -- workspace 库内单调
  event_id       TEXT NOT NULL UNIQUE, -- 生产者稳定身份；重试去重
  session_id     TEXT NOT NULL,
  execution_mode TEXT NOT NULL,      -- production | simulation
  run_id         TEXT,
  task_id        TEXT,
  type           TEXT NOT NULL,        -- run.started / step.thinking / step.text /
                                       -- step.tool_call / step.tool_result /
                                       -- decision.requested / decision.answered /
                                       -- effect.intent / effect.dispatching /
                                       -- effect.settled / effect.unknown / run.finished ...
  occurred_at    TEXT NOT NULL,
  cause_id       INTEGER,              -- 因果链：结果指向触发它的事件
  schema_v       INTEGER NOT NULL,
  payload_digest TEXT NOT NULL,        -- 同 event_id 不同内容必须 Conflict
  payload_json   TEXT NOT NULL
)
```

规则：

- 先落库再分发；SSE 按 `seq` 尾随，重连用 `after=seq`。
- **事件身份**：`event_id` 由生产者按事实稳定生成，workspace 库内唯一；相同 ID 与 digest 的重试返回原事件，相同 ID 不同 digest 返回 Conflict，不得静默覆盖或重复 append。按实际读取路径建立 `(execution_mode, session_id, seq)`、`(execution_mode, run_id, seq)`、`(execution_mode, task_id, seq)` 索引，生产列表、恢复和 Main 投影默认过滤 `execution_mode='production'`，禁止用 payload JSON 表达式扫描替代这些关联查询。
- **游标语义**：`seq` 与 `after` 都是 workspace 级游标；服务端按 session/run/task 过滤，过滤造成的全局序号空档不算丢帧。Snapshot/Resync 与空 replay 页都返回当前 `high_watermark`，客户端可推进游标。未知、未来或早于保留历史的游标必须返回 `Resync(snapshot, high_watermark, reason)`，不得静默跳过；实时与回放竞争按 seq/event_id 去重。
- **流式回放**：Snapshot 后按既有 256 条页大小读取并向客户端逐页吐出，最多预取一页；不得像当前实现那样先把 after 之后的全部事件装进 `VecDeque`。内存占用必须与回放总条数无关，实时事件继续使用有界广播，lag 时 Resync；`after=0` 与百万级历史也只能分页处理。
- thinking/text 按 D7 在工具调用与 assistant 消息结束边界聚合，不逐 token 落库，也不引入时间窗定时器；实时 SSE 与历史回放使用同一边界事件。空段不写；崩溃时未闭合段可丢失，`run.interrupted` 必须记录 `incomplete_tail=true` 与 `last_persisted_seq`，不得把尾部不完整的回放伪装为完整。
- `session_events` 与 `media_evidence` 只保存媒体元数据、hash 和证据引用，不保存图片/视频字节、base64 或签名 URL；媒体字节沿用现有文件/按需播放边界，provider 附件也不得被事件 sink 序列化。
- 事件是事实；**Task/Run/Job/投影**可由事件重建。`effect_intents` 与 `decisions` 是带事件镜像的权威状态机：每次状态迁移与对应 `effect.*` / `decision.*` 事件在同一事务写入，不允许只写一边；它们不能仅靠重放事件恢复 dispatch 许可。
- schema 版本随事件记录；greenfield 下暂无迁移，但读路径必须能识别未知版本并拒绝静默降级。
- **设备事实快照（D2）**：组合根先从平台库读取目录与声明，生成带 `observed_at`、`declaration_hash`、驱动版本的 `DeviceFactsSnapshot`，再把快照写入 workspace 事件；事件提交事务不得回查平台库。目录读取失败时不创建 Run，而是持久化 `trigger.unavailable`/Supervisor 错误，包含 workflow、trigger 与下一边界；历史回放使用事件内快照而非目录当前值，独立恢复后以 hash/版本显式报告目录漂移。

### 保留与背压

- v1 `session_events` 全量保留，不按行数、固定容量或时间删除，不做 compaction；这与“不新增固定事件配额”一致。未来若需保留策略，必须先做可校验的全量归档（事件数、hash、schema 版本）与快照，再决定清理；过期游标只能走显式 Resync。
- Agent 在下一步推进前等待事件 append 提交，形成自然背压，禁止为了绕开慢盘而丢事件或直接分发未落库事实。记录 append latency、DB/WAL bytes、写入错误、snapshot/rebuild lag 与 SSE resync；持续写入恶化与磁盘耗尽必须告警并使 Run 明确失败，不能静默降级。
- SSE 慢消费者沿用有界广播 + Resync，不反向丢弃持久事件；遥测 `hub_ledger` 的保留与背压不在本版改动范围。

### 副作用状态机

```text
effect_intents(
  effect_id      TEXT PRIMARY KEY,   -- hash(workspace + run + tool_call)，稳定身份
  session_id     TEXT NOT NULL,
  task_id        TEXT NOT NULL,
  run_id         TEXT NOT NULL,
  tool_call_id   TEXT NOT NULL,
  tool_name      TEXT NOT NULL,
  request_json   TEXT NOT NULL,      -- 内部可执行请求；不得直接经公开 SSE 暴露
  request_digest TEXT NOT NULL,      -- 规范化 tool/target/request 的 digest
  idempotency_key TEXT NOT NULL UNIQUE, -- 派生自 effect_id，传给 driver/provider
  external_ref   TEXT,               -- driver_call_id / provider operation id
  state          TEXT NOT NULL,      -- prepared / dispatching / cancelling /
                                     -- completed / failed / not_applied / unknown /
                                     -- cancelled / cancelled_unknown
  state_version  INTEGER NOT NULL,   -- 每次迁移递增，CAS/fencing
  result_json    TEXT,
  created_at     TEXT NOT NULL,
  updated_at     TEXT NOT NULL,
  UNIQUE(task_id, tool_call_id)
)
```

**身份与可恢复请求**：`effect_id` 只由 workspace/run/tool_call 稳定派生，不包含会随参数规范化变化的 digest；同一 effect_id 不同 request_digest 必须 Conflict。`idempotency_key=effect_id` 并传到 driver/provider；重新决策必须产生新的 tool_call/effect/key。`request_json` 保存恢复与对账所需的内部可执行请求，`external_ref` 保存设备或 provider 返回的操作身份。公开 `step.tool_call` 与 `effect.*` 事件只携带 effect_id、工具名、脱敏参数摘要和安全结果，不直接序列化 request_json。

状态与事件一一对应，写入同一事务：

| 状态 | 事件 | 含义 |
|---|---|---|
| `prepared` | `effect.intent` | 意图已持久化，尚未发送 |
| `dispatching` | `effect.dispatching` | 唯一物理发送许可 |
| `cancelling` | `effect.cancelling` | 已记录停止请求，等待外部明确终态 |
| `completed` | `effect.settled` | 外部系统确认已执行，`result_json` 有值 |
| `failed` | `effect.failed` | 外部系统明确拒绝且不可重试（参数/前置条件/权限） |
| `not_applied` | `effect.not_applied` | 确认未执行；可安全重新决策 |
| `unknown` | `effect.unknown` | 无法判定是否执行；必须对账 |
| `cancelled` | `effect.cancelled` | 外部系统明确确认已停止 |
| `cancelled_unknown` | `effect.cancel_unknown` | 停止结果未知；Task 以 `failed(cancel_unknown)` 结束，不假称全停 |

- `prepared` 落库后才允许 `dispatching`；`dispatching` 是唯一物理发送许可。
- **真源声明（D3）**：`effect_intents` 是唯一执行、dispatch 许可与恢复真源，不是事件投影；每次状态迁移与对应事件在**同一事务**内写入，禁止只写事件不写状态或反之。`device_jobs` 是可由事件重建的设备视图，不再独立迁移状态；worker/provider 只报告 accepted/progress/result 等事实，由 Harness 在同一事务写 effect、事件、Job 投影与 wake。命令参数、`driver_call_id`、progress、result、stop 与证据完整保留。外部 ACK 只表示命令被接收，不得冒充物理动作已完成；物理完成需设备事实或证据另行确认。
- **终态唤醒原子性（D3/D4 延续）**：`completed/failed/not_applied/cancelled/cancelled_unknown` 的 effect 终态、对应 `step.tool_result`、Run/Task 状态与 `task_wake_outbox` 必须在同一事务提交；重复终态只返回当前事实，不新增 wake。`unknown` 不是可继续 Run 的终态，必须保持阻塞并对账。
- **failed 与 unknown 的区分**：外部系统明确返回不可重试的拒绝 → `failed`；超时、断连、无查询能力、记录缺失 → `unknown`。`unknown` 不得自动重试。
- **崩溃恢复**：进程在 `dispatching` 期间崩溃时，无论崩溃发生在物理发送前还是发送后，只要无法由唯一存活 permit 持有者证明未发送，重启恢复都原子提升为 `unknown` 并写 `effect.unknown`。只有仍在运行、且能证明尚未物理发送的 permit 持有者才能走 `cancel_before_send`；不得把已提交许可当作 `prepared` 重发。
- 只读/生成类工具直接执行；有后果的工具走保护边界；语义不确定的失败关闭。
- `task_wake_outbox` 保留为事件/唤醒的投递 outbox；效果投递与唤醒投递分开记账。

### 对账端口与失败关闭

Harness Core 不认识设备，只依赖端口：

```rust
#[async_trait::async_trait]
pub trait EffectReconciler: Send + Sync {
    /// 查询外部系统（设备/Job/provider）对某个效果的最终状态。
    async fn settle(&self, intent: &EffectIntent) -> ReconcileOutcome;
}

pub enum ReconcileOutcome {
    /// 已确认执行；result 进入 effect_intents 与事件。
    Settled(EffectResult),
    /// 已确认外部执行失败且不可重试。
    Failed(EffectResult),
    /// 已确认停止；仅 cancelling 状态可接受。
    Cancelled(EffectResult),
    /// 已确认未执行；可以安全地重新决策。
    DefinitelyNotApplied,
    /// 无法判定（设备不可达、记录缺失、provider 无查询能力）。
    Unknown { reason: String },
}
```

- `Settled(result)` → effect 置 `completed`，写 `effect.settled`，`result_json` 记录结果、证据引用与 actor（人工确认时为确认人）；然后唤醒原 Task。
- `Failed(result)` → 仅在外部确认原操作已经终止且不再运行时，effect 置 `failed`，写 `effect.failed`；结果、证据与错误原因进入 `step.tool_result`，Run/Task 状态和 wake 同事务提交。**取消/停止请求失败不构成物理停止证据**，必须返回 Unknown 并映射 `cancelled_unknown`，不得以 failed 让父任务假称全停。
- `Cancelled(result)` → 仅允许 `cancelling` → `cancelled`，写 `effect.cancelled` 并同事务唤醒父级；其他状态返回 Conflict。
- `DefinitelyNotApplied` → effect 置 `not_applied`，写 `effect.not_applied`；Run 以「动作未执行」的工具结果继续。若模型再次决定执行，**创建新的 effect intent（新的 tool_call id 与 effect_id）**，不重用旧身份。
- `Unknown { reason }` → `unknown` 状态保持 `unknown`，`cancelling` 状态转为 `cancelled_unknown`；均不得自动重试。在**同一事务**内幂等地确保存在一条 `kind=effect_reconciliation` 的 `decisions` 记录（`decision_id` 由 `effect_id` 派生，重复恢复不会产生重复决策）。对应 Run 保持阻塞，直至对账得到明确结果。
- 账号可见文案固定为：「设备动作结果未知：<effect 摘要>。已完成现场确认后选择“已执行”或“未执行”。」
- 每次对账尝试写 `effect.reconcile_attempted` 事件；设备不可达或 Job 记录缺失都归入 `Unknown`，失败关闭。
- **自动/人工单赢家（D5）**：自动与人工都经同一 reducer/Db 事务，只有 expected state=`unknown`、版本匹配且 reconciliation decision 仍为 `requested` 时，自动结算才可提交。人工 `answered` 先提交即赢得对账，即使 Task 暂停、尚未 consume，自动结果也只能记录为审计事实。自动先赢时，effect 终态与 pending decision `withdrawn(auto_reconciled)` 同事务；人工可推进时，decision 消费与 effect 终态、`step.tool_result`、Run/Task 状态、wake 同事务。迟到者返回当前结果或明确 Conflict，不覆盖终态、不重复唤醒；原终态不可变；错误自动对账只能通过新证据启动独立、可审计的纠正/补偿 Workflow，任何新 effect 都使用新 ID/key。

### 决策生命周期

`decisions` 是 v1 唯一的审批/决策真源，带事件镜像，状态与事件在同一事务写入。状态机：

```text
requested → answered → consumed
requested → expired
requested → withdrawn
```

按 kind 区分的答案词汇：

| kind | 答案 |
|---|---|
| `tool_approval` | `approved` / `denied` |
| `effect_reconciliation` | `applied` / `not_applied` |
| `other` | 不透明载荷，由消费方解释 |

**按 kind 的过期规则**：`tool_approval` 可由调度器在 `expires_at` 过期；`effect_reconciliation` 必须 `expires_at IS NULL`，不能普通过期，也不能因 Task 取消而撤回，只能由人工消费或 `withdrawn(auto_reconciled)` 结束。startup 遇到 `answered` 未消费时保留该答案：Task 可推进则消费并结算/唤醒，暂停则继续等待。任何 unknown Effect 必须始终存在 actionable reconciliation path，并有 expiry/startup 测试。

事件集：`decision.requested`、`decision.answered`、`decision.consumed`、`decision.expired`、`decision.withdrawn`；payload 携带 `kind` 与答案。

- 记录字段：`decision_id`、`kind`、`state`、`session_id/run_id/task_id/effect_id`、`subject`（tool_call/effect 摘要）、`options`、`created_at/updated_at`、`expires_at`、`answer`、`answer_actor`、`answer_event_id`、`consumed_at`、`consumed_by`。
- **派发门控**：需要审批的工具在**同一事务**内创建 `prepared` effect 与 `requested` 决策。
  - `answered`：同事务写 `decision.answered` 与持久 wake，answer 只能是该 kind 的合法值。Task 暂停时保留原 wake，不消费；可推进时再消费。
  - `approved`：同一事务写 `decision.consumed` 与 `effect.dispatching`；**提交成功后**才物理派发。
  - `denied`：同一事务写 `decision.consumed`、`effect.not_applied` 与 Run wake；不派发。
  - `expired` / `withdrawn`：作为无 answer 的终止状态，effect 仅在 prepared 未发送时置 `not_applied` 并唤醒 Run；不得把 expired/withdrawn 写进 answer。
- **消费规则**：requested 只能接受一次答案；重复同答案返回当前状态，不同答案 Conflict。一个决策只能消费一次，重复消费返回当前状态，不重复派发或唤醒。answer+consume 可以同事务写两类事件，暂停时只允许 answer，恢复后才允许 consume。
- **过期**：调度器扫描 `expires_at`，写 `decision.expired`，并按上述规则把 effect 置 `not_applied`。
- **撤回**：分两类处理，禁止一律改 effect。Task 取消或工具调用不再适用时，只对 `prepared` 且未发送 effect 的 `tool_approval` 写 `decision.withdrawn` 并置 `not_applied`；`effect_reconciliation` 不得因此撤回。自动对账先赢时的 `withdrawn(auto_reconciled)` 只关闭 pending decision，effect 由对账结果决定。
- **对账决策**：`applied` → effect 置 `completed`，`result_json` 记录结果、证据引用与 actor（人工确认人）；`not_applied` → effect 置 `not_applied`；两者都随后唤醒原 Task。
- 重建口径：`decisions` 是权威表；`decision.*` 事件是审计镜像，不能只靠事件重建"谁可以派发"。

### 权限与敏感信息

- 所有新写面统一使用 **Agent 管理权限**：Task 创建、暂停/恢复/取消、工具审批、设备调用/停止、effect reconciliation、Workflow create/edit/enable/disable、模板实例化、dry-run 创建、HarnessCommand、压缩检查器 CAS/rebuild、dead-wake retry、workspace backup/restore。读取 Task/Run/Workflow/Decision/证据沿用 workspace 读取权限。所有请求在打开 workspace DB 前完成 tenant/workspace 与角色校验，人工对账记录 `answer_actor` 与证据引用，不能匿名提交。
- `request_json` 仅供内部 dispatch/reconcile 使用，公开 SSE、普通投影和默认管理 DTO 不得返回；公开事件使用工具描述生成的脱敏 `arguments_summary`。嵌套 password/token/secret 字段必须有脱敏测试。
- workspace DB 与备份可能包含内部请求和设备数据，文件权限与备份访问至少等同于现有平台库；本版不宣称静态加密。密钥引用优先由适配器在 dispatch 时解析，避免把可复用凭据写入事件。
- **Prompt/内容注入**：设备遥测、视频元数据/OCR、知识文档和外部事件均是不可信输入，以明确数据围栏进入 prompt；其中“忽略审批/调用工具/泄露密钥”等文本永远不能成为权限或执行依据。模型输出仍需 schema、ToolDescriptor、策略合成与 Effect 门，证据 ID 必须存在。Skills/Workflow 只能由管理角色按版本安装，UI 不直接渲染未转义 HTML。
- **路径与依赖安全**：workspace 路径只由注册表 ID 派生，备份/恢复拒绝越界、symlink 与未关闭 pool；不新增动态代码依赖或插件包。provider 密钥继续使用现有环境/安全配置，不写日志、事件或模板。

### 错误分类与救援

| Method/codepath | 具体错误类 | Rescue/原子行为 | 用户可见结果 |
|---|---|---|---|
| Workflow save/validate | ValidationError / UnknownReference / PolicyWeakening | 保存前拒绝，不追加 revision | 字段级错误，不调度 |
| Provider capability 检查 | CapabilityUnavailable | 模型调用前 Run failed(capability_unavailable)，零 Effect | 缺失能力与恢复建议 |
| Supervisor tick/schedule | StorageError / InvalidCron / ClockAnomaly | tick 记录失败；无重复 slot，按 XD8 跳过过期并告警 | stalled/degraded 与原因 |
| Main/Subagent provider 调用 | ProviderTimeout / RateLimited | 沿既有有界 backoff/Run 预算，不无限重试 | 临时失败与下一次恢复 |
| Provider 输出 | ProviderEmpty / ProviderRefused / MalformedTaskOutcome / InvalidEvidenceRef | 分别写 step.error，Run failed(outcome_invalid/refused)，不伪造成功或证据 | 明确输出失败，不触发后续 Effect |
| 模型工具调用 | UnknownTool / InvalidArguments / PolicyDenied | 工具边界拒绝，零 prepared Effect | 工具与参数错误 |
| Db.apply_workspace_transition | CasConflict / StorageLocked / CommitUnknown | CAS 重读；锁重试整个事务；未知提交先按稳定 ID 去重 | 冲突可重试，无重复动作 |
| Approval/Decision | DecisionConflict / DecisionExpired / PermissionDenied | 保留当前状态与原 wake，暂停按合同延后消费 | 当前答案/冲突/权限错误 |
| Effect dispatch | DeviceRejected / DeviceTimeout / DeviceUnreachable / EffectUnknown | 拒绝→failed；不确定→unknown并对账，禁止盲重试 | 真实失败或未知，不伪成功 |
| Worker/provider 迟到结果 | StaleVersion / DuplicateFact | CAS 丢弃状态覆盖，事实按稳定 ID 去重 | 不覆盖当前终态 |
| HarnessCommand | DuplicateCommand / CommandExpired / InvalidTarget / QueueConflict | 不重复执行；过期/无效目标明确终止；单头 FIFO | 当前命令状态与原因 |
| Dry-run | SnapshotMissing / SimulationDispatchBlocked | 固定 snapshot 缺失即失败；Effect/生产 wake 硬阻断 | simulation 错误，不影响生产 |
| Event decode/projection | UnknownSchema / CorruptEvent / ProjectionMismatch | 停止静默降级，保留旧快照并显式 Resync/rebuild | 数据版本/恢复状态可见 |
| SSE 连接 | UnknownCursor / Lagged / SlowConsumer | 分页 replay，lag Resync，连接关闭可重连 | 明确恢复，不丢帧伪装 |
| Workspace create/migrate | PoolOpenError / MigrationFailed / IntegrityFailed | 单 workspace unavailable，其他继续 | 告警与迁移原因 |
| Workspace restore | RestoreFailed / PoolBusy / BackupCorrupt | 回滚保留 DB，重新打开但保持 unavailable | 恢复失败与其他区可用 |
| Backup/delete | IoError / WorkspaceBusy | 不删除/覆盖可用 DB，先 quiesce/close | 失败原因与重试 |
| 所有 HTTP/API mutation | PermissionDenied / CrossTenantAccess | 在打开 workspace DB 前拒绝，不泄漏目标是否存在 | 权限错误，无跨区数据 |

所有错误日志携带 workspace/workflow/task/run/effect/command 与稳定 request/cause ID，参数仅使用脱敏摘要。没有 catch-all 后继续；未知错误进入明确失败与告警，不伪装成成功。

### 恢复与投影

- 启动时扫描活跃 workspace 库中非终态 Run 与**所有非终态 effect**，按状态分支处理：
  - `prepared` 且关联决策为 `requested` → 等待，不派发；若 Task 已 `cancelling`，撤回决策并置 `not_applied`；
  - `prepared` 且决策 `state=answered` 且 `answer=approved` 未消费 → 仅在 Task 可推进时，同一事务消费决策并写 `effect.dispatching`，再派发；
  - `prepared` 且决策 `state=answered` 且 `answer=denied` 未消费 → 消费决策，effect 置 `not_applied` 并唤醒 Run；
  - `prepared` 且决策 `state=expired/withdrawn` → effect 置 `not_applied`；
  - `prepared` 且无决策 → 按工具策略继续（需要审批的必须补建决策；Task `cancelling` 时禁止派发）；
  - `dispatching` → 原子提升为 `unknown` 并写 `effect.unknown`，同一事务幂等确保 `effect_reconciliation` 决策存在；
  - `cancelling` → 对可恢复 driver 调用按同一 effect/job id 重断言停止；无法恢复或结果不明时置 `cancelled_unknown`，不静默重发；
  - `unknown` → 幂等确保对账决策存在，重试 `EffectReconciler`，Run 保持阻塞；
  - `completed/failed/not_applied/cancelled/cancelled_unknown` → 终态，按结果与 Task 控制状态继续或结束。
- **Command 恢复（XD10）**：启动扫描所有 `requested` command，先由扫描器及消费事务分别检查 `expires_at`；过期只写 `command.expired`，不得消费。
  - `interrupt`：目标 Run 仍有当前模型调用时才消费并 abort 其 token；目标不存在/已终态则 rejected/superseded。
  - `steer`：目标 Run 活跃且下一次模型调用尚未开始时才消费，将 guidance 纳入下一次 prompt 并唤醒；否则 rejected/superseded。
  - `queue`：保持 requested 并按 command seq 排队；只有到前序边界时才消费，并在同事务创建实际输入/Task wake；父/子终态或取消时标 superseded。
  - 所有 consume 都在同一事务写 command 状态、command 事件、目标 Run/Task 与 wake；崩溃前无动作，提交后按 command_id 幂等，重复恢复不重复 abort/指导/入队。

### 完整恢复矩阵

| Effect state | Decision/外部输入 | 唯一允许动作 |
|---|---|---|
| prepared + requested tool_approval | Task 活跃/暂停 | 等待；取消只允许撤回未发送 approval |
| prepared + answered(approved/denied) | 未消费 | 活跃时消费并分别 dispatching/not_applied+wake；暂停保持 answered/wake |
| prepared + expired/withdrawn | 未发送 | not_applied+wake |
| prepared + 无 decision | 工具策略 | 需审批先补 requested；否则 CAS dispatching；取消禁止 |
| dispatching | 进程重启/失去 permit | unknown + reconciliation decision；不得按 prepared 重发 |
| unknown + requested | Settled/Failed/DefinitelyNotApplied/Unknown | 自动 CAS 分别 completed/failed/not_applied/保持 unknown；Unknown 只记 attempt |
| unknown + answered(applied/not_applied) | 人工答案已赢 | 活跃时消费并分别 completed/not_applied+wake；暂停等待；自动结果不覆盖 |
| unknown + 无 decision | 恢复 | 同事务创建永不过期的 reconciliation decision；失败告警，不推进 Run |
| cancelling | Cancelled/Failed/Unknown | 分别 cancelled/failed/cancelled_unknown+wake；不得重用旧 ID 重发 |
| completed/failed/not_applied/cancelled/cancelled_unknown | 迟到事实 | 返回当前终态，不覆盖、不新增 wake |

| Decision state | 恢复动作 |
|---|---|
| requested tool_approval | 可过期；请求继续等待 |
| requested effect_reconciliation | 永不过期；自动对账与人工回答仍可竞争 |
| answered | 答案固定；活跃才 consume，暂停保留 wake |
| consumed/expired/withdrawn | 终态；重复输入返回当前，不重新打开 |

| Command state | 恢复动作 |
|---|---|
| requested 且未过期 | 按 target_task_id+seq 保留；interrupt/steer 仅在目标仍有效时消费，queue 到边界消费 |
| requested 且过期 | command.expired，不执行 |
| consumed/rejected/superseded/expired | 终态；重复恢复不重新执行 |

未列出的 EffectState × DecisionState × ReconcileOutcome × CommandState 组合均为非法持久状态：写 `recovery.invalid_state`、workspace 标 unavailable/degraded 并告警，禁止 dispatch、consume 或自动修复成可执行状态。

- 恢复不是"继续执行代码"，是"从持久状态重新进入"；模型不重放已提交的工具结果，设备不重复执行已知效果。
- 投影（Task/Trace/Workbench）由事件折叠；`projection_snapshots` 只加速启动，可随时丢弃重建。
- `projection_snapshots(projection_name, subject_id, last_seq, projection_version, state_version, state_json, updated_at)` 以 `(projection_name, subject_id)` 为主键；`projection_version` 表示投影格式，`state_version` 是每次更新单调递增的并发版本。启动读取匹配版本的快照并只折叠 `seq > last_seq` 的尾部，版本不匹配才走完整 rebuild。不得在每次请求或启动时默认重放全部历史。
- 非终态 effect/Task 的恢复扫描使用对应状态/部分索引；投影按 `(session/run/task, seq)` 增量更新，禁止用全事件扫描代替日常读取。完整 rebuild 是带进度与错误报告的维护操作，可删除快照后从事件重建全部投影，用于校验。
- **压缩检查器（X4，XD5 已批准）**：显示压缩 seq 范围、projection_version、证据引用与最后完整点。重建与比较固定同一 `projection_version + last_seq` 边界，先在临时投影计算 canonical state/hash 并与同边界当前投影比较；匹配后仅以 expected `last_seq/state_version` CAS 替换快照。重建期间的新 append、比较后版本变化或 hash 不匹配都保留最新快照并显示差异/重试，不得以旧快照覆盖新快照。对 session facts、Task/Run、Effect/Decision 和外部系统只读，只允许 CAS 替换 projection snapshot，全程零 dispatch。

### Core 边界（D1 已批准）

```text
crates/agent/              -- 通用 Harness Core：Main/Subagent 共用 Loop/Tool/Prompt/rig 端口 +
                              事件、状态机、效果、决策、控制、投影；rig 保持私有适配器
crates/runtime/            -- Device Hub（继承）
crates/db/                 -- 平台库 + workspace 库实现、迁移、索引
apps/cloud/                -- Host/Supervisor、组合根、HTTP/SSE、thing-agent 应用与设备适配器
```

不新建 `crates/harness` 或 `crates/harness-rig`。`crates/agent` 不得依赖 `crates/runtime` 或设备类型；thing-agent 应用与设备实现移入 `apps/cloud`，设备工具、声明、上下文段通过端口由组合根注入。crate 是否改名为 `harness` 不在 D1 范围内，仍待决定。

**状态迁移调用契约（D4）**：`core` 只放跨层共享值；`agent` 提供纯 `reduce(state, fact) -> Transition`，不做 I/O；`db` 在事务内重验 `expected_version` 与前置状态，原子写入 effect、事件、Job 投影和 wake；`apps/cloud` 统一编排 load/reduce/apply，Conflict 时重读后重算。只有 `dispatching` 提交成功后才允许物理 dispatch，SQLite 事务内不得调用设备或 provider。

所有多表写入统一经过 `Db::apply_workspace_transition`，不在审批、对账、取消等调用方各写一套事务。SQLite code 5/6 等瞬态锁错误按既有有界策略重试整个 load→reduce→apply，而不是只重试 `BEGIN IMMEDIATE`；若 COMMIT 结果不确定，先按稳定 effect/event/wake ID 读取并去重，再决定是否重试，防止重复事实或物理 dispatch。

```text
Db.load → agent.reduce → Db.apply_tx(expected_version)
                              ├─ effect_intents
                              ├─ session_events
                              ├─ device_jobs projection
                              └─ task_wake_outbox
                           commit → cloud/worker 物理 dispatch
```

### 控制与扩展

- 控制面：steer / interrupt / pause / cancel / queue 都是持久事实，不只是 UI 动作。
- **Pause（继承已批准契约）**：只停止后续 Run 与新 effect 派发，不 abort 当前 Run token、不取消在途 effect；恢复时按等待关系回到 `waiting_job/waiting_watch/needs_approval` 或恢复 Run。
- **Cancel（继承 D6-task-cancel）**：CAS 进入 `cancelling` 并写事件，abort 当前 Run token，工具派发前再次检查；只撤回 `prepared` 未发送 effect 的 `tool_approval` 并置 `not_applied`，pending wake 标 dead，取消 owned watch，按同一 effect/job id 停止活跃 effect。`effect_reconciliation` 保留到结果明确。重复取消幂等，不重复 stop。
- **提交后竞态**：dispatcher 在 `dispatching` 提交后、物理发送前再次检查 Task cancelling/token。若取消已提交，唯一 permit 持有者在未发送前提下把 effect 置 `not_applied(cancel_before_send)`；若取消在检查之后提交，此次发送按在途 effect 处理，进入 `cancelling` 并按同 ID stop，不能假称未发送或撤回对账决策。单实例内仍只有一个 permit 持有者可发送。
- 所有所属活跃 effect 得到明确终态后 Task 才能 `cancelled`；任一 `cancelled_unknown` 使 Task 以 `failed(cancel_unknown)` 结束。`dispatching/unknown` 的外部结果不能靠取消抹掉，仍须对账；迟到的重复终态只保留事实，不再次唤醒。设备级 `Stop all` 仍是独立操作。
- **统一命令（XD10=A）**：`commands` 保存 `seq INTEGER PRIMARY KEY AUTOINCREMENT` 与唯一 `command_id/kind/target_task_id/target_run_id/actor/payload/created_at/expires_at/state`，状态为 `requested/consumed/rejected/superseded/expired`；事件镜像与实际迁移同事务。command_id 去重，目标必须显式，不能隐式向所有 Main/Subagent 广播。FIFO 按 `target_task_id + seq`，使用 `(target_task_id, state, seq)` 索引；同一目标每次事务只消费最早的有效 command，不阻塞其他目标的独立队列。
- **Interrupt**：只 abort 当前模型/provider 调用并写 `run.interrupted`，Task 保持活跃以接受后续 steer/输入；不取消在途 Effect，不改变 workflow 调度。
- **Steer**：持久 guidance 在下一次模型调用前按 seq 消费，不隐式 abort 当前调用；Run 已终态或命令过期则拒绝/标 expired，不在重启后静默消费陈旧指导。
- **Queue**：后续输入/任务按 command seq 持久 FIFO；pause 保持 pending，cancel 将未消费命令标 superseded，恢复后只按序消费仍有效的命令。没有新固定配额，使用持久 outbox 背压与 oldest-pending 指标。
- 决策：统一 decision register；审批问题、答案、消费状态、未知效果对账都记账。
- 扩展面仅限已批准的 `ToolDescriptor`、版本化 `skill_refs` 与 `WorkflowDefinition`；不声明 loops/UI panels 插件清单，不引入动态插件包 DAG。
- 工具运行时：注册与暴露分离；`ToolDescriptor` 单一声明 name/schema、prompt summary、只读/effect 类型、required capabilities、审批策略、参数脱敏与通用展示元数据，由注册表生成 LLM 可见工具子集、catalog API、策略门和前端展示。宪法只写通用工具使用规则，前端消费通用 step/effect/decision 事件，新增设备工具不得再手改 Core 或前端事件名单。策略、审批、沙箱在工具边界执行。
- **策略合成**：Workflow `approval_policy` 只能收紧 ToolDescriptor 与设备/声明的强制策略，不能降低审批、权限、资源仲裁或联锁要求。保存 revision 时计算并持久化 effective policy 与 tool/policy digest；prompt 和 dispatch 都使用同一合成结果，当前强制策略与固定 revision 不一致时失败关闭并要求新 revision，不允许旧配置绕过新强制要求。测试包含模板试图关闭强制审批的拒绝用例。
- 上下文管线：记忆分层、Skills 渐进加载、压缩产生血缘事件（后续轴）。

### 交互边界与状态覆盖

- 提交使用稳定幂等键，按钮在请求中禁用但服务端仍去重；编辑配置时以 current_version 做 stale-submit Conflict，用户看到“配置已更新，请比较后重试”，不能覆盖他人新版本。
- 离开页面/切换 Task 只释放当前 SSE 与媒体资源，不取消后端 Run；旧 generation 的响应和事件必须丢弃。恢复连接从最后确认 seq 续传，未知游标显式 Resync。
- 空 workflow/无到期任务显示明确空态；大列表与 backlog 使用分页/增量渲染，不把全部子任务或历史事件一次塞进 DOM。
- dry-run 始终显示 simulation banner；错误、partial replay、重建冲突和非视觉 provider 都有可恢复说明，不使用假进度、假在线或伪造百分比。
- 键盘可完成模板实例化、审批、对账与控制；焦点、Esc、屏幕阅读器状态文本、对比度与至少 44px 触摸目标沿用现有 Runtime 设计约束，新面板不得只在桌面悬停时显示关键信息。

| Feature | Loading | Empty | Error | Success | Partial |
|---|---|---|---|---|---|
| Workflow 列表 | 保留旧列表并标记刷新 | 无 enabled 配置与模板入口 | 读取/鉴权错误可重试 | 当前版本/启停/下一 wake | 部分 workspace 不可用逐区显示 |
| Supervisor 面板 | 显示最近已知 tick | 正常空闲，不显示 stalled | 错误/停滞事实与恢复 | 健康 tick 与调度时间 | 单区故障不掩盖其他区 |
| Dry-run | simulation 进度 | 无 snapshot 明确提示 | capability/config/simulation guard | 模拟结果与证据 | 缺尾部明确标记 |
| Task/Run 详情 | 保留快照 | 尚无步骤 | provider/tool/effect 错误 | 完整步骤与结果 | waiting/unknown/迟到事实 |
| 压缩检查 | 保留当前快照 | 尚无压缩 | hash/CAS 不匹配 | 等价并替换 | 保留最新快照并重试 |

## Success Criteria

1. 一次 IoT 任务 Run 的全部过程可在 `session_events` 回放；前端断线重连后按 `seq` 续上，不丢步。
2. 在设备动作中途 kill 进程，重启后 `dispatching` 被提升为 `unknown`，先对账再决定；不出现重复设备动作。

## CEO Expansion Evaluation

### 10x Check

从“人工触发一次 Task”升级为“系统持续发现、协调和验证工作”。同一个 Workflow 引擎支撑巡检、协同、视频和节能，新增场景只增加配置，理想情况下用约 2x 的核心实现成本获得 10x 的持续运行价值。

### Platonic Ideal

运维用一份声明描述目标、设备、证据与约束；Host 持续调度，Main Agent 负责跨任务协调，Subagent 在隔离上下文中执行。所有动作经过设备联锁、审批与 Effect 安全边界，所有结果有证据，所有恢复不重复物理动作，所有主上下文都能从持久事实重建。调试配置可以先 dry-run，线上状态、下一次唤醒、失败原因和恢复路径对操作者透明。

### Dream State Mapping

```text
当前：触发器 + 一次性 Task + 多套审批/事实/硬编码
  → 本期：两层 Main/Subagent + WorkflowDefinition + 持久事件/Effect/恢复
  → 12 个月：配置即场景、持续协同、证据闭环、独立扩展、可验证运维
```

- **DR4 — 模板实例化旅程（pending）**：三份模板有后端要求，没有说明从模板到可运行 Workflow 的字段、预览、默认启停和完成页。建议 pending 方案为模板选择 → 实例参数与引用校验 → 可选 dry-run → 保存为 disabled → 详情显式启用；主行动始终只有一个，不能保存即偷偷调度。备选是直接实例化并启用，不适合有设备后果的配置。
- **DR5 — Supervisor 恢复操作（pending）**：面板字段已列出，但 dead-wake retry 的选择、确认、pending/结果、无权限表现未定义。建议 pending 方案为逐条 dead wake 展示原 event_id、失败原因与目标，使用「按原事件重试」确认；请求中保留列表并禁用该行，结果就地显示，无权限只读，不做批量隐式重试。备选是跳既有 Admin 页，但上下文切换更长。
- **DR7 — dry-run 的 snapshot 选择与结果回程（pending）**：固定 revision/snapshot 是硬合同，但用户尚无法知道在哪里选、错误归属哪里、结果如何回到编辑器。建议 pending 方案为从固定 revision 的编辑详情进入独立 simulation Run；snapshot picker 显示 seq/observed_at，banner 全旅程持续存在，结果复用通用 Run 投影但完全只读，并提供「返回此版本」。备选是对话框内 dry-run，但完整过程与证据空间不足。
- **DR8 — 压缩检查器的比较与冲突呈现（pending）**：已有 canonical hash/CAS 规则，没有定义用户看到的差异、可执行动作和冲突后的焦点。建议 pending 方案为显示固定边界、hash、证据范围与最后完整点；只有同边界匹配才允许「替换投影快照」，mismatch/CAS conflict 保留最新快照并显示差异与「重新比较」，不自动重试或 dispatch。备选是只读检查不配替换动作，但不符合已接受的 CAS 维护操作范围。
- **DR9 — 写操作的可见反馈（pending）**：启停、恢复重试与 CAS 替换没有统一的请求中/成功/失败外观。建议 pending 方案为触发按钮进入 pending、保留已读内容、结果就地更新并用文字宣布；失败保留可修正上下文，不只发短暂 toast，也不显示假进度。备选是全局 toast-only，会让关键恢复结果失去持久上下文。
