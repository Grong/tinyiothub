# 设计外部声音：AI 子系统全链路梳理 spec — §3 前端 AI 中心独立设计评审

- 日期：2026-10-12
- 评审对象：`docs/superpowers/specs/2026-10-12-ai-consolidation-design.md`（重点 §3 L101-133 + §1 词汇表）
- 参照实现：`web/src/ui/views/dispositions.ts`（710 行）、`web/src/ui/views/ai-ops.ts`、`web/DESIGN_SYSTEM.md`（Tuya 深空视觉语言）

## Litmus（7 项）

| # | 问题 | 判定 | 一句话理由 |
|---|---|---|---|
| 1 | 品牌首屏可辨 | **NO** | §3 通篇无视觉层规定——Tuya 深空语言（玻璃拟态/渐变边框/发光状态点）进不进 #/ai 完全未定，首屏品牌归属悬空 |
| 2 | 单一强视觉锚点 | **NO** | 信任选择器+统计条（顶栏）、E1 自述、「需要你」、Run 流四个候选争第一眼，spec 未指定锚点 |
| 3 | 只扫标题能懂 | **NO** | 「Run 流」「Trust Mode」是工程师词不是用户词；词汇表收编了异名但没有规定面向用户的可见标题词 |
| 4 | 每节一职 | **YES** | 五块（顶栏/自述/需要你/Run 流/配置）职责单一不重叠，这是 §3 最干净的部分 |
| 5 | 卡片必要性 | **YES** | 复用 dispositions 现状卡片（标题行+理由行+动作区），卡片是审批动作的最小必要容器，不滥 |
| 6 | 动效增益 | **NO** | spec 零动效规定——DESIGN_SYSTEM 的 reveal/reduced-motion 纪律、SSE 新 run 插入的入场处理均无归属 |
| 7 | 去阴影仍高级 | **NO** | 无视觉处理规定即无法判定；单色纪律（dispositions 现行）与深空高级面（DESIGN_SYSTEM）两条路线 spec 都没选 |

**Litmus 总结**：2/7。§3 是合格的 IA 草图，不是可实施的设计 spec——视觉层与状态层整层缺失。

## 发现（按严重级排序）

### F1 [critical] 「需要你」与 Run 流的主次关系未定——IA 根决策悬空

**问题**：ASCII 树把「主视图：Run 流」列在「需要你」之前，且只给 Run 流标了"主视图"字样。但现状 dispositions 用实际设计证明了相反层级才是对的：默认 tab=「需要你」（行动优先），空态=「一切正常」产品故事时刻。运维打开 AI 中心的第一问永远是"有没有事需要我"，不是"AI 今天在干嘛"。同时「需要你」的形态本身未定——是 tab（dispositions 现状）、置顶区（钉在 Run 流上方）、还是 Run 流的筛选预设——三种形态的信息层级完全相反。

**修法**：spec 明确裁定一句：「需要你」为第一屏锚点——有待办时置顶区呈现（带计数），清零时塌陷为「一切正常」一句话；Run 流为其下主体。或裁定 tab 制并说明理由。二选一，不留斜杠。

### F2 [critical] 信任切换对"在途 run 的影响"无规则——确认弹窗文案写不出来

**问题**：E2 要求切换确认弹窗"提示影响面：当前在途 run 是否受影响"，但 spec 没有定义什么算受影响。D9 裁定统一循环后所有 run 过信任门——那么一个正在 investigating 的 run，在工作区从"需要你批准"切到"全自动"的中途，它的后续动作按新档还是旧档？立即生效、下一 run 生效、还是在途 run 跑完旧档？后端语义不定，弹窗文案就是空话；后端语义定了但和弹窗文案不一致，就是信任事故（用户以为批了的其实自动执行了）。

**修法**：spec 增加一条信任门生效规则（建议：切换对切换后新触发的 run 生效，在途 run 沿用触发时档位——实现最简单且可解释），并规定确认弹窗文案模板（"当前 N 个进行中的 run 将按原模式跑完；新任务立即按「全自动」执行"）。

### F3 [critical] 信任选择器的控件形态与三档措辞未定——一等 UX 前置名不副实

**问题**：信任选择器被定为"常驻一等 UX"，但 §3 只给了三档名字（需要你批准/只读自动/全自动）。控件形态（segmented control？dropdown？带描述的 radio card？）未定；三档各自的含义解释（每档 AI 能干什么/不能干什么）无责任方；"只读自动"本身语义矛盾（只读为何叫自动？）——它会做什么？巡检只读不发提案？还是提案但不执行？一档名字有歧义，整个选择器就是个谜语。新用户面对一个无解释的常驻三档开关，这是 onboarding 的第一道坎。

**修法**：裁定控件形态（建议 segmented control + 当前档一句话说明）；为每档写一句用户语言的行为描述进 spec；重命名"只读自动"（如"自动巡检，动手先问"）；档位解释文案归属=E2 确认弹窗+配置抽屉信任区共用单一事实源。

### F4 [high] 统计条指标收敛未裁定——两条旧统计条合并必丢东西，丢谁没人定

**问题**：归并映射写"摘要进顶栏统计条"，但现状有两条：dispositions 头部（今日消化/需要你/延迟 p50/反馈学习数）和 ai-ops 今日摘要卡（autoCount/pendingCount/errorCount）。4+3 个指标合并成一条统计条，砍谁留谁 spec 未定。实现者自由发挥的结果是要么 7 个指标全堆（顶栏变仪表盘，稀释锚点），要么随手砍（p50 延迟这种反映 AI 健康度的指标丢了无人察觉）。

**修法**：spec 给出统计条最终指标清单（建议 3 个以内：今日消化 / 需要你 / 异常数），被砍指标注明去向（进配置抽屉的诊断区或砍掉）。

### F5 [high] 统一 Run 流的状态徽章词表与颜色纪律未定

**问题**：现状 dispositions 的 BADGE_MAP 覆盖 11 个状态词（分析中/自行闭环/需要你/执行中/闭环/转工单/已拒绝/未受理×2/巡检正常），heartbeat 侧还有自己的状态词。归一后"一种 Run"在统一流里的徽章词表是什么？更关键的是颜色纪律：dispositions 现行设计明确规定"单色纪律——颜色只出现在需要行动处（琥珀●）"，而 Run 流要用"来源徽章区分三类 trigger"——三类来源若各给一个彩色徽章，直接违反单色纪律，整个流变成彩条。

**修法**：spec 附统一状态词表（Run verdict × disposition 的展示词全集）+ 明确来源徽章用中性样式（灰底文字标签或图标），行动色只属于「需要你」。

### F6 [high] E1 今日自述的状态矩阵与视觉权重完全缺失

**问题**：E1 规定了输入（当日 run summary 集合）和时机（加载时聚合一次、按日缓存），但四个状态全无规定：① LLM 挂/超时——自述块显示什么（隐藏？「今日自述暂不可用」？整页报错？）；② 全新工作区第一天零 run——"我今天做了什么"无话可说什么；③ 跨日缓存边界——23:59 打开的缓存到 00:01 还算"当日"吗（按日 key 的时区与刷新规则）；④ 加载中——自述位置先占位（布局跳动）还是骨架。另外自述的视觉权重未定：它在顶栏与 Run 流之间，是一句话正文灰字还是卡片？做成卡片它会抢「需要你」的锚点；做成一句话又可能和统计条混淆。

**修法**：补 E1 四状态表（挂→静默隐藏不留残壳；零 run→显示引导文案"还没开始干活，去配置心跳任务"；缓存按本地日期+首次可见刷新；加载中→骨架一行）。裁定视觉形态=一行正文级文本，不用卡片。

### F7 [high] 批准→执行的回链缺失——"我批了之后它干了没有"的旅程断点

**问题**：情绪弧：打开 #/ai（安心/有事）→ 看「需要你」→ 读提案理由 → 批准 → **然后呢？** 批准后提案对应的执行 run 会出现在 Run 流里，但 spec 没有规定提案与执行 run 的互链。现状 dispositions 批准后只是 toast「已批准，开始执行」+ 刷新列表——用户日后回翻时无法从"我当时批的那个提案"找到"它执行得怎么样"。审批闭环的最后一环（批准的后果可追溯）在 spec 里不存在。

**修法**：规定批准动作产生的执行 run 与提案行互链（提案行显示"已批准 → 查看执行 run"；执行 run 卡片标注来源提案）；至少提案行在执行完成后展示执行结果的回填状态。

### F8 [high] 视觉语言归属未定——Tuya 深空 vs 单色纪律，spec 一句话没有

**问题**：DESIGN_SYSTEM.md 定义了完整 Tuya 深空体系（玻璃拟态/渐变边框/发光状态点/3 层浮动阴影），dispositions 现行设计是克制的单色纪律。#/ai 作为归并后的第一 AI 入口，走哪条路线 spec 完全没提。这直接决定 litmus 第 1/7 项的失败，也是实现者最大的自由发挥空间——做出来和 dispositions 不像一家人，或过度装饰变成发光仪表盘，两种灾难概率各半。

**修法**：spec 加一句视觉基调裁定（建议：延续 dispositions 单色纪律为本体，深空元素仅限状态点/主按钮等 DESIGN_SYSTEM 已令牌化的微件；不引入浮动卡/渐变边框），并指明沿用 DESIGN_SYSTEM 令牌（space/radius/duration 禁止硬编码）。

### F9 [medium] 空态矩阵缺失——产品故事时刻在归并中无家可归

**问题**：现状有三个精心设计的空态：「需要你」清零=「一切正常」+ 今日摘要；「全部」空=「大脑还没开始干活」；筛选后零结果无专门文案。归并后：① 全新工作区（零 run、零提案、未配心跳）的 #/ai 首日空态——这是新用户对产品智能的第一印象，spec 未写；② E4 筛选零结果（"没有匹配的运行"vs"还没有任何运行"必须区分，前者要给清除筛选出口）未写；③「需要你」清零态归谁（若 F1 裁定置顶区，清零后是否塌陷）未写。

**修法**：补空态文案矩阵三行（首日空态=引导去配置；筛选零结果=文案+清除筛选按钮；需要你清零=沿用「一切正常」）。

### F10 [medium] E6 SSE 断连与 run_recorded 幂等规则未定

**问题**：E6 规定 run_recorded 推内容而非刷新信号，但：① 断连细条是否沿用现状 sse-banner 模式（「实时更新已断开，点击刷新获取最新」）未提；② 断连期间错过的 run 重连后如何补拉（推内容的模式下没有整表刷新兜底，错过即缺失）未定；③ run_recorded 推内容 + 60s 轮询整表刷新并存时，同一条 run 从两个通道到达的去重/幂等规则未定（现状 reconcileExpanded 只管展开卡，不管行去重）。

**修法**：沿用 sse-banner；规定重连后整表补拉一次；规定 run_recorded 按 run_id 幂等插入（已存在则更新不重复插入）。

### F11 [medium] 配置是抽屉还是分区未定——可链接性与 a11y 责任差一个量级

**问题**：归并映射写「#/agents → 配置抽屉/分区」，斜杠=未定。抽屉（overlay：要 focus trap/Esc/焦点还原，不可深链，刷新丢失上下文）与独立分区（路由可达如 #/ai/config，可深链可分享，刷新不丢）是可发现性与实现成本完全不同的两种形态。agents 现状 4 tab（设定/权限/技能/心跳）内容量不小，塞进抽屉会很挤。

**修法**：裁定形态（建议：配置=独立分区路由，顶栏只放入口按钮；抽屉只用于轻量快速操作如信任详情查看）。若坚持抽屉，spec 须引用 DESIGN_SYSTEM §7.4 的 overlay a11y 清单作为验收项。

### F12 [medium] E5 步骤级反馈的交互密度未定——详情页可能变成按钮丛林

**问题**：E5 写"trace 步骤/结论的点踩直接进 judgment_feedback，详情页挂入口"。一条 trace 常有 10+ 步，每步挂 ✓/✕ 按钮的视觉噪音与误触率是灾难级的；只在结论挂反馈则丢失"哪一步错了"的定位精度。粒度（步骤级/结论级/两者）与控件形态（常驻按钮/hover 显现/单选模式）未定。

**修法**：裁定粒度（建议：结论级常驻 ✓/✕ + 步骤级 hover 才显现单个"这步有问题"入口，点击后该步骤 id 随反馈写入）；规定同一 run 已反馈过的视觉回执（防重复提交）。

### F13 [medium] 新用户与第 1000 次用户的差异未被考虑——常驻元素的生命周期缺失

**问题**：信任选择器常驻顶栏：新用户需要解释（三档是什么），老用户一个月不碰一次却永远占着顶栏最贵位置。E1 自述按日缓存：新用户第一天它无话可说，老用户第 100 天它可能已是视觉噪音（每天一句话逐渐套路化）。spec 对这两类常驻元素都没有"可折叠/记住折叠态/新手态 vs 熟手态"的任何梯度设计。

**修法**：轻量处理即可——信任选择器旁一次性新手提示（首次访问 tooltip，看过即记录）；E1 可折叠且折叠态持久化（localStorage）。各一句话进 spec。

### F14 [medium] Run 流的分页/筛选维度/返回态保留未提沿用——现状已有正确答案

**问题**：dispositions 现状已解决的一批硬问题：PAGE_SIZE=20 游标分页+「加载更多」、展开卡 reconcile、防重入 pendingIds、键盘 a11y（Enter/Space 展开、Esc 收起+焦点交还）、时间戳三档格式。§3 只写"卡片+时间线组件直接复用现状"，对这些行为级设计资产是否沿用只字未提。另外 E4 筛选的维度（trigger 类型/结果/关键词——能按设备筛吗？按时间范围？）和"从 #/ai/runs/{id} 返回时筛选态与滚动位置是否保留"未定——日后回翻旅程（第 3 次使用后的高频路径）的体验全压在这两个未定点上。

**修法**：spec 加一行"行为沿用清单"（分页/防重入/键盘/reconcile 照 dispositions 现状搬家）；E4 补筛选维度全集与返回态保留规则（建议 hash query 承载筛选态，天然可回退可分享）。

### F15 [medium] 卡片级深链的归并去向未定——patrol_tick 行现行跳 #/ai-ops，归并后跳哪

**问题**：归并映射只覆盖顶层入口和 run 详情路由，但 dispositions 卡片内部有卡片级跳转（patrol_tick 聚合行点击跳 #/ai-ops；「查看完整轨迹」链 #/ai-ops/runs/{id}；「打开工单」链 #/tickets/{id}）。归并后 #/ai-ops 整体废弃，这些卡片内深链的目标分别是什么（跳 Run 流的巡检筛选预设？跳 #/ai/runs/{id}？），spec 未逐条映射。实现者漏一条就是一个死链。

**修法**：归并映射表补卡片级深链三行（聚合行→#/ai?trigger=heartbeat；完整轨迹→#/ai/runs/{id}；工单不变），并要求重定向测试覆盖卡片级来源。

## 维度小结

| 维度 |  verdict |
|---|---|
| 1. 信息层级 | 五块职责干净，但锚点未指定且 Run 流 vs 需要你的主次与现状证明的正确答案相反（F1/F4/F6） |
| 2. 缺失状态 | 状态层整层缺失：E1 四状态、E2 在途语义、E4 零结果、E6 断连幂等、空态矩阵、配置加载态全未规定（F2/F6/F9/F10） |
| 3. 用户旅程 | 断在批准之后（无执行回链 F7）与回翻路径（无返回态 F14）；新/老用户差异未考虑（F13） |
| 4. 具体性 | 泛模式级：控件形态/措辞/徽章/指标/抽屉 vs 分区全留给实现者（F3/F4/F5/F11/F12） |
| 5. 埋雷决策 | F1（IA 主次）、F2（在途语义）、F3（选择器形态）三条不定，实现必返工；F8（视觉归属）不定，实现必撕裂 |

**总评**：§3 的方向（run 为组织单位、信任前置、单入口）是对的，词汇表收口也扎实；但它目前是一份"布局草图+行为注记"，距可实施的设计 spec 差一整层状态矩阵+三条 IA 级裁定。建议在 writing-plans 拆 Phase 3 之前，先把 F1/F2/F3 三条 critical 裁定落回 spec——其余 high/medium 可在实现期以设计评审跟进，但这三条不定，前端开工即埋雷。
