## 本 PR 的原始问题

产品中四个运维功能（报警中心、工单、心跳、事件日志）各自生长，没有一条数据流真正
穿过 AI 大脑：报警默认去处是人（通知渠道全打桩），用户被报警淹没且不知如何处置。
本 PR 把报警的默认去处翻转为「AI 处置流」——报警产生即由 thing-agent 调查判断
（噪声/可自愈/需人工），人只处理例外。详细问题陈述见设计文档：
`~/.gstack/projects/Grong-tinyiothub/chenguorong-worktree-fix-event-heartbeat-defects-design-20260911-161121.md`

## Vision

### 10x Check
不是报警管理工具，而是一个不需要人盯着的运维班次：AI 是 7×24 值班员，
用户早上看一份摘要 + 处理 3 件 AI 已查过半的例外。2026 AIOps 景观里
97% 报警是噪声、60% 企业上自愈、分阶段自治是主流——但所有玩家聚焦
K8s/云原生，IoT 设备舰队的 agentic AIOps 是空档。TinyIoTHub 的处置流
正站在这个空档上。

### 差异化位置（landscape 校验）
行业最佳实践 = 先降噪 → 加护栏 → 分阶段自治。本 PR 的「影子判断 + 分级
出口 + 信任起步 ApprovalRequired」与之精确对齐，且比通用 AIOps 多一层
IoT 特有的物理 blast radius 敬畏（执行必须分级信任）。

## 术语表

- **处置流**：报警 → AI 调查 → 判断（verdict）→ 按出口流转的完整数据流。
- **判断 / judgment**：AI 对一条报警的结构化处置结论，落 `judgments` 表，八态状态机。
- **verdict 三出口**：noise（噪声，静默归档）/ self_healable（可自愈，需审批）/ needs_human（需人工，转工单）。
- **kill switch**：workspace 级配置 `ai_triage_enabled`，关闭时报警走原人工路径。
- **预算闸**：每 workspace 每日判断数上限（当前硬编码 100），超限不再发起 AI 调查。
- **flapping 防抖**：同 thing+rule 已有未终态判断时，新报警不重复发起调查。
- **O11 dedup**：thing-agent dispatch 层的既有去重机制（6h 窗口 + ack 抑制 7 天）。
- **影子期**：P0 阶段，AI 全量判断但执行全走人工审批，攒反馈数据。
- **triage mode（T-6 新增）**：`annotate`（只记录判断，不动报警）/ `suppress`（判 noise 才抑制报警）。
