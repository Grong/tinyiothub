# 我删掉了自己写的 Workflow 引擎

> 一次 IoT Agent Harness 的重构复盘：三个失败面，和一个我很久才承认的错误。

## 先说结论

2026 年 11 月 3 日，我给这个项目的 Agent 架构写了一份相当完整的设计计划：版本化的 Workflow 模板、零副作用 dry-run、Supervisor 健康面板、主上下文压缩检查器、24 小时 soak 演练。三轮评审，分数 6/10 → 8/10 → 7/10。

11 月 7 日，我把它删了。

不是修，是删。`Workflow` 这个抽象从产品路径上整体退役，连带着定义、修订、模板、dry-run、runner 和 simulation 端点一起下掉。

原因不是它写得不好。恰恰相反——**它写得太好了，好到它能可靠地保证一件根本不该被保证的事。**

## 第一版长什么样

核心假设很符合工程直觉：运维人员用一份声明描述目标、设备、证据和约束，系统据此调度执行。声明大概是这个形状：

```
objective              要达成什么
trigger                什么时候做
device_selector        对哪些设备做
source_selector        看哪些数据源
tool_ids               允许用哪些工具
skill_refs             加载哪些技能
required_capabilities  需要哪些能力
approval_policy        什么情况要人批
evidence_policy        什么算证据
```

九个字段。填完，系统就知道该干什么了。

愿景听起来非常对：**新增场景主要增加配置，而不是增加代码。** 巡检、视频分析、节能，都是同一套 `WorkflowDefinition` 的不同配置。想加一个"空压机巡检"，写份声明就行。

为了让这套东西可靠，我加了一整套保障设施：

- **X2** 历史 snapshot + scripted provider 的零副作用 dry-run——上线前验证配置
- **X3** Supervisor 健康面板——24×7 调度、错误、恢复都要可见
- **X4** 主上下文压缩检查器——临时重建 canonical state 比对 hash，失败保留旧快照
- **X6** 24 小时 soak 与故障演练 runbook
- **M1** 停机期间过期 cron 全部跳过并记 missed，不补跑、不合成
- **C1** 统一 steer / interrupt / queue 持久命令，支持幂等与恢复

评审也很认真：第一轮 6/10，15 组问题修订；第二轮 8/10，又修 6 组；第三轮 7/10，10 组问题写回设计。三轮封顶，没有第四轮。

到这里，一切看起来都像一个负责任的架构。

## 三轮评审，评的不是产品

这里是我后来才想明白的第一件事。

那三轮评审评的是什么？是设计文档的一致性、边界是否写清、失败模式是否覆盖、术语是否统一。这些都很重要。

但**没有一轮在问：这个系统能不能把一件真实的事从头做完？**

因为当时它确实做不到。

而我在给它加 dry-run、加健康面板、加压缩检查器。

于是就有了那个荒谬的画面：**一个还跑不完一次真实巡检的系统，已经有了一套保证它稳定运行 24 小时的演练方案。**

我把这个现象记下来，因为它会反复出现，而且每次都伪装成"工程严谨"：

> 当你发现自己在给一个还没跑通的循环加可靠性设施时，先停下。那不是严谨，那是在给错误的方向做加固。

dry-run、健康面板、压缩检查器，这些设施的前提是"它已经在工作了，我要让它更稳"。前提不成立时，它们只是在放大沉没成本——因为你会因为"这么多配套设施都建好了"而更不愿意承认主循环是错的。

## 三个失败面

真正让我决定推翻的，是三条很朴素的使用反馈。

**一、Agent 干不成真实任务。**

多步任务中途走偏，最后给你一份看起来完整、实际上欠了好几项的报告。它不是报错，是"顺利完成"——只是没做完。

**二、不知道如何开始。**

九个字段。一个工厂运维看到 `required_capabilities` 和 `evidence_policy`，第一反应不是填写，是关掉页面。

我设计了灵活性，交付的是启动成本。

**三、看不到它在干什么。**

只能看到工具调用流水，看不到"现在在处理哪件事、为什么这么判断、还剩几步"。想干预的时候，找不到介入点。

第二和第三条，其实不是 UI 问题。它们指向同一个东西：我在设计一个**需要被正确使用才能工作**的系统，而不是一个**默认就能工作**的系统。

有人用一句话把这个差别说穿了，我记了很久：

> 我需要的是一个完整的大脑。大脑是一直存在的，我只需要告诉它需要注意什么、需要干什么活，它就会执行；如果没有明确指示，它按默认执行。

Workflow 的哲学是"先声明，再工作"。用户要的是"先有大脑，再补充关注点"。

这不是加个默认值能解决的，是入口顺序反了。

## 三个结构性冲突

把失败面翻译成架构语言，就是三处硬冲突。

### 入口冲突：声明式把"探索"排除在外了

声明式的前提是：你能在开始之前把要做的事想清楚。

但运维的真实情况是——你只知道"3 号楼最近不对劲"。至于哪里不对、要不要动手、动哪个，得在看数据的过程中才知道。

声明式要求你先填完 `device_selector`，才能开始看数据。而"看数据"本身，就是发现问题的那一步。

把探索挡在门外，系统就只能执行你已经知道答案的任务。那它就不需要智能了。

### 执行冲突：两个循环，谁也说不清自己在干嘛

当时后端并存着两个执行器：交互式 chat 循环，和自治的 thing-agent 循环。

一个工具 `dispatch_thing_task` 把活异步甩给后者，然后回一条报告。

用户看到的是：一段一段的日志。不是一个连续工作的智能体。两套 prompt 拼装、两份状态、两条恢复路径。

更麻烦的是，"甩单"这个动作在语义上就承认了分裂——主循环不打算对这件事负责到底，它只是转交。

**Agent 的价值在于"一直负责到做完"。任何形式的异步转交，都在削弱这个价值。**

### 过程冲突：可观测性不是加面板

事件模型当时只有工具级的 `TurnEvent`：`tool.called`、`tool.returned`。

没有任务的 span，没有技能的 span，没有提问的 span。

所以前端没法回答"现在在干哪件事"。它只能显示工具调用流水。我后来想要的"计划中 1/3"，在这个事件模型里根本没有对应字段。

这就是为什么加健康面板没用：**面板能显示一个黑箱的体温，但没法告诉你它在想什么。**

可观测性的起点是事件模型，不是 UI 组件。事件里没有 span，面板上就永远只能画曲线。

## 换成了什么

新模型只有一句话：**一个常驻大脑，多个会话，五个 primitive。**

- 每个 workspace 一个常驻 Assistant（产品文案里叫"大脑"）。它的身份、记忆、默认职责来自 md 文件。
- 一个 Assistant 可以开多个 Session：对话、定时巡检、事件处置。共享身份与记忆，不共享上下文。
- **技能是工作手册**（怎么干），**主 prompt 是值班表**（什么时候、干什么）。
- 默认零配置可运行；所有默认值都能通过改 md 或直接对话覆盖。

五个 primitive，全部对齐主流 harness 的做法：

| Primitive | 做法 |
|---|---|
| Skill | `SKILL.md` + frontmatter；上下文只放索引，调用时注入正文（渐进披露） |
| TodoWrite | `{ todos: [{ content, status, activeForm }] }`；整体替换；同一时间一个 `in_progress` |
| AskUserQuestion | 1–4 个问题，每题 2–4 个选项，可多选，阻塞当前 turn |
| Task（子代理） | 同步、独立上下文、返回结构化报告、只做一层 |
| Plan mode | 这一期没做 |

架构上钉了三条边界：

1. **触发与执行分离**——调度器只产生 wake，不拼 prompt、不跑循环。
2. **Assistant 与 Session 分离**——一个大脑，多个会话，会话之间不共享对话上下文。
3. **安全层不动**——policy / trust / Effect / Decision / unknown 对账 / 审批，全部原样保留在工具层。

第三条是这次重构里最重要的一条。后面会讲为什么。

## 最难放弃的执念：确定性

Workflow 之所以诱人，不是因为它好用，是因为它**确定**。

每一步都声明过，系统可以保证执行、保证顺序、保证不遗漏。这是工程上非常舒适的东西。

换成 `todo_write` 之后，任务清单是模型自己维护的。系统不解析、不校验、不强制。技能正文里写编号步骤，模型读完自己建成 todo——可能漏一项、可能改顺序、可能中途重排。

我做这个决定之前犹豫了很久。最后把它写进了 Non-Goals，白纸黑字：

> 不能硬保证每一项都执行。

这是我第一次在架构文档里主动放弃一个保证。

但换来的是：模型可以在执行中发现问题、重排计划、向用户提问。**这是"能干活"的前提。**

反过来想就通了：如果一件事从头到尾都能被精确声明，那它本来就不需要 agent，一个 cron job 加一个脚本就够了。agent 的价值恰恰在"你还没完全想清楚"的那部分。

**确定性是有价格的。Workflow 用确定性换掉了适应能力，而适应能力才是你买 agent 的理由。**

## 代价清单

删掉的：

- Workflow 定义 / 修订 / 模板 / dry-run / runner
- simulation 与 dry-run 端点
- 前端 `harness-workflow-*` / `harness-templates` / `harness-dry-run` 视图
- `AutonomousAgentProvider` 及其独立 prompt 拼装
- `dispatch_thing_task`（异步甩单），换成同步的 `spawn_subagent`
- 两个循环合成一个

保留的，一条都没动：

- Effect / Decision 单赢家、unknown fence、对账、恢复语义
- policy / trust / approval
- `hub_ledger` 审计账本
- `session_events` 时间线、SSE、MCP
- skills loader、ToolRegistry

**推翻的是"怎么组织工作"，不是"怎么保证安全"。**

这两件事极容易被混在一起，导致一个常见的误判：以为换架构就要重写安全层，于是不敢换；或者反过来，换架构的时候顺手把安全层也"简化"了。

我的分法很明确：组织工作的方式可以整体重来，物理世界的安全边界一行都不许动。删代码也分批——Batch 0 到 Batch 6，共七批，每批独立验收，禁止大爆炸。

## 三条可以搬走的教训

**第一，在设计文档上得高分，和产品能干活，是两件独立的事。**

三轮评审从 6 分到 8 分再到 7 分，评的是文本一致性。同期产品一次真实任务都跑不完。评审越认真，越容易给人"方向已经验证过"的错觉。

**第二，给没跑通的循环加可靠性设施，是沉没成本的前奏。**

dry-run、健康面板、压缩检查器、soak 演练——这些都应该在"它已经能跑"之后出现。提前建它们，唯一的效果是让你更难承认主循环错了。

**第三，声明式适合你已经完全理解的过程，agent 适合你还没完全理解的过程。**

运维现场大部分属于后者。你想让系统替你做决定的那部分，恰恰是你自己还说不清的那部分。用声明式去接它，等于要求用户先替系统想清楚——那系统就没有创造任何价值。

## 现在

这个项目叫 TinyIoTHub，现在的定位是 **IoT agent harness**——给物理世界写 harness。

它离完美还很远：驱动还在补，旧路径还没删干净，迁移做到一半。但至少有一件事变了——**一次真实任务可以从头跑到尾了**，而且你能在时间线上看见它每一步在干什么。

如果你也在做类似的事，我的建议只有一句：

> 先让它能笨拙地把一件事做完，再让它可靠地做一万次。

顺序反了，你会得到一套非常完备的、什么都不干的系统。
